# Как проверить сборку по плану 010

Инструкция для будущих проверок. Новые результаты заносить в `specs/010-graph-visuals/verification.md` при первом прогоне. Файлы и видео с названиями заметок Raincoat хранить локально вне публикуемого репозитория. Для иллюстраций в Git подходит синтетическая сцена.

## 1. Сохранить эталон

До обновления открыть установленный Raincoat, сверить активную версию с манифестом, сохранить хеши установленных runtime-файлов и зафиксировать версию Obsidian, устройство, тему, размер панели, DPR, render scale, положение камеры, фильтры, пресет и физику. На одной сцене сохранить три кадра с повторяемыми положениями камеры. Записать короткое видео медленного приближения, наведения на хаб, перетаскивания и нескольких секунд после отпускания. Сохранить исходные данные сравнения до первого пробного жеста, чтобы повторные прогоны начинались из одной раскладки.

Для beta.1 и beta.2 воспроизвести одинаковый drag на стабильной модели с заданными позициями и временем. Добавить контрольный несвязанный узел и цепочку соседей. Сравнить траекторию под курсором, положение узла в момент отпускания, положение через 1, 3 и 4 секунды и время успокоения соседей. Синтетический результат дополнить сравнением с записью Raincoat. Если ощущение различается, следовать решению этапа 0. Тесты каждой неизменённой версии запускаются с её собственными ожиданиями.

## 2. Запустить проектные проверки

В корне отдельного рабочего дерева с выбранной базой выполнить `npm ci` при отсутствии установленных зависимостей. Штатная последовательность для свежей рабочей копии приведена ниже.

```sh
npm ci
npm run verify
npm run build
git diff --check
```

Проверки физики уже входят в `verify`. Для диагностики отдельно доступны `npm test -- src/workers/layoutDrag.test.ts` и, на базе beta.2, `npm test -- src/workers/towForce.test.ts`. К изменениям внешнего вида добавить содержательные тесты для геометрии, размещения подписей, сохранения настроек и остановки анимаций. Производительность GPU и видимый результат проверяются в живом рендерере.

## 3. Сравнить производительность

Из корня проекта собрать имеющийся стенд и открыть страницу в одном браузере с WebGL.

```sh
node bench/build.mjs
python3 -m http.server 4173 --bind 127.0.0.1
```

Адрес страницы - `http://127.0.0.1:4173/bench/index.html?nodes=5000&camera=3d&worker=3d&seed=42&scale=standard`. Для других сценариев использовать `nodes=10000`, `camera=2d&worker=2d` или `scale=high`. В новой версии стенда параметр `appearance=modern` явно включает новые эффекты измеряемого рендерера. Результат доступен в `window.__graphBenchmark` и строке `RESULT_JSON`. Один и тот же стенд запускать на исходной beta.1 и кандидате. По кадру и счётчикам убедиться, что во время замера показаны связи, папки и подписи, предусмотренные оформлением проверяемой версии.

| Что зафиксировать | Как сравнивать |
|---|---|
| Данные | Стабильный seed, 5 000 и 10 000 заметок с ориентиром до 3 рёбер на заметку, фактическое E после устранения повторов, одинаковые seed-позиции, камера и сценарий событий. Включить папки, кириллицу и длинные имена. Отдельная плотная фикстура содержит хаб с более чем 600 соседями и встречные рёбра. |
| Режимы | Для каждого размера пройти глобальный 3D с физикой в трёх измерениях, затем 2D с двухмерной физикой. В 3D с глубиной по кластеру/возрасту проверить правильность проекции отдельно. Для локального графа выполнить нативный сценарий появления соседей, вращения, переключения 2D и смены центральной заметки. |
| Взаимодействие | Активная раскладка, панорамирование, приближение и удаление, орбита в 3D, hover, drag с отпусканием при работающем worker, статичная сцена, скрытие и возврат. Различать панорамирование и орбиту по фактическим изменениям камеры. Подтверждать попадание в нужный узел и движение хотя бы одного связанного соседа. |
| Метод | Прогреть обе версии. Минимум три повторения сценария на версию в каждом режиме и размере, чередуя исходную и новую. Один Mac, окно, DPR, тема, качество, режим питания и частота дисплея. Повторно использовать входные данные и длительность выборки. У имеющегося стенда это 4 с активного действия и 30 с покоя. Таймаут раскладки указывать явно. |
| Выход | В каждой строке записать версию, режим, N/E, сценарий, медиану FPS по rAF, p95 длительности кадра, количество кадров >33 мс, остановки >500 мс, фактические отрисовки, ошибки. В покое считать отрисовки за 30 с. Дополнительно записать время прохода подписей, число кандидатов/показанных меток и стоимость обновления рёбер при сравнении вариантов. |

Правило сравнения зафиксировать до правок рендера. Для каждого активного сценария сравнить медиану показателей трёх прогонов кандидата с диапазоном исходных прогонов. FPS не должен устойчиво падать ниже нижней границы, p95 и доля длинных кадров - выходить выше верхней. При широком разбросе повторить обе стороны в сопоставимых условиях и указать неопределённость. Новые ошибки, остановки и заметные рывки разобрать отдельно. Цель для 5k - 60 FPS в активных сценариях. Печатать измеренные значения и отдельно отмечать достижение цели и отсутствие регрессии. В покое критерием служит число реальных отрисовок. Исторический порог стенда 50 FPS сам по себе не закрывает задачу.

## 4. Нативная проверка, установка и возврат

1. До обновления подготовить настроенный вид и сохранить пресет и состояние рабочего пространства. После обновления сначала восстановить прежнюю вкладку и сверить её с исходным кадром. Закрыть лист и обычной командой создать новый граф в том же vault, затем снова восстановить старый вид из сохранённого состояния. Проверить оба варианта после перезапуска, также открыть старый импортированный профиль. Нажатие команды при уже открытом листе только возвращает существующий граф.
2. Для каждой готовой сборки выполнить проверки проекта, тест в изолированной сцене и сравнение с эталоном. Сначала проверить 3D, затем 2D. Пройти [визуальный контракт](contracts/visual-behavior.md) в обеих темах. Дополнительно проверить узкую панель, перенос окна, поиск с 1/8/9 результатами, Explore, маршрут, PNG в скрытой вкладке, кириллицу, совпадающие и длинные имена. Навести на узел с последним уникальным именем после последовательного просмотра других групп.
3. При установке в Raincoat сохранить резервную копию прежних файлов плагина `graph-insight`. Перенести `main.js`, `manifest.json` и `styles.css` проверенной сборки. Сравнить версию и хеши runtime-файлов, перезагрузить плагин, открыть граф и проверить консоль. Затем повторить тот же нативный сценарий. В случае сбоя вернуть прежние runtime-файлы, перезагрузить плагин и проверить восстановленный вид. Файлы настроек, позиции, пины и содержимое vault сохраняются.
4. К каждому из трёх этапов приложить проверенный номер сборки или локальный идентификатор с хешем, пару кадров исходного и нового вида, изменение времени кадра и точку проверки владельцем. В финале - три пары кадров на разных расстояниях, короткая запись движения, обе темы, таблица 5k/10k и перечень непроверенных условий.
