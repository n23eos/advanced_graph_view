# План улучшения Advanced Graph View — после критического пересмотра

Дата: 2026-09-07. Статус: реализовано и проверено в этом проходе.

## Результат внедрения

### Проверка стабильного релиза — 2026-09-09

Цель: выпустить 0.9.0 после проверки beta. Найдены и исправлены конфликт
`display:flex` с `hidden` у строк фильтра и отложенный перехват фокуса.
Регрессионные тесты проверяют вычисленный CSS и сохранение фокуса checkbox.
Браузерная проверка настоящего компонента на 1002 тегах: поиск, Tab/Space,
Escape и визуальное скрытие строк успешны. Полный Obsidian повторно не проверялся.
Shared memory недоступна (timeout); актуальное состояние сохранено здесь.
Следующий шаг: отправить release-коммит, дождаться CI и опубликовать тег 0.9.0.

Этапы 1–4 и подтверждённые оптимизации выполнены. В строке поиска появились
активные ограничения с адресным снятием и восстановлением вида; отдельное
состояние нулевого результата больше не выглядит как пустое хранилище. Меню
тегов и папок получили поиск, корректный Escape и доступные состояния. Стили
flat/glow/ring отделены от палитры с миграцией старых настроек. Tooltip поясняет
метрики размера и цвета, а обычные подписи избегают пересечений, сохраняя
приоритет выбранных, наведённых и маршрутных заметок.

Частые обновления поиска объединены по кадру, adjacency и Focus distances
кешируются до смены модели, выбранные фильтры компилируются вне цикла узлов, а
устаревшие задачи content-index отбрасываются. Новый фильтр-бенчмарк показывает
среднее время 0,155 мс для 3k, 0,536 мс для 10k и 2,790 мс для 50k узлов.
Исторически дорогим участком остаётся физическая раскладка: текущие замеры 10k
дали около 50,9 мс на tick в 2D и 92,2 мс в 3D, поэтому renderer и hit-test не
переписывались без доказанной пользы.

Ручная проверка выполнена в Obsidian на тёмной теме и хранилище из 4712 заметок:
поиск с нулём результатов, Show all, меню фильтров, возврат фокуса, три стиля
узлов и пояснения tooltip работают. Адаптивность и контраст дополнительно
покрыты существующими тестами; аппаратная матрица разных масштабов интерфейса
в этот локальный проход не входила.

## Основания и ограничения

Изучены текущий код поиска, фильтров, композиции видимости, подписей, настроек, легенды, клавиатурных событий; README, CHANGELOG, прежние планы и UI-спецификация. Рабочие изменения поиска из предыдущего прохода учитываются как уже внесённые, но ещё не выпущенные.

Скриншот `assets/advanced_graph_view_nebula.jpg` просмотрен только как пример визуального языка: расположение панели инструментов на нём устарело относительно текущего кода. Первоначально живой Obsidian и пользовательские сценарии не были проверены; это ограничение снято в ходе внедрения в объёме, описанном выше. Более широкие выводы об удобстве для разных пользователей остаются гипотезами до внешнего пользовательского тестирования.

## Продуктовое решение

Основной пользователь — человек со средним или большим хранилищем, который хочет найти заметку, разобраться в её связях или привести базу в порядок. Частота затруднений пока неизвестна: данных наблюдений нет.

Цель следующего этапа: пользователь понимает, что видит, может найти нужное и восстановить понятный вид без перебора настроек. Успех измеряется завершением этих сценариев и временем до результата. Локальные тестовые наблюдения достаточны; телеметрия не нужна.

Решение: **go для небольшого этапа ясности состояния и фильтров**. Новые режимы, крупная переделка рендера и большой рефакторинг не входят в первый релиз.

Уже есть и повторно не планируется: Tasks, Simple/Expert, адаптивность по ширине панели, Focus/Explore и breadcrumb, сохранённые фильтры с менеджером, экспорт Markdown-карты, «Что изменилось?», системный reduced motion, восстановление после отказа воркера/WebGL.

## Найденные основания для работ

| Область | Что видно в коде | Пользовательское следствие / степень уверенности |
|---|---|---|
| Состояние фильтрации | `GraphView.recomputeVisual()` объединяет hard query, теги/папки, скрытые кластеры, timeline и скрытые узлы; `pushSearchUi()` выбирает статус только по soft/hard query | Сужение графа может не объясняться строкой поиска. Подтверждено структурой кода |
| Счётчик подсветки | `softMatched` увеличивается и для узлов, скрытых другими условиями | «Подсвечено N» может превышать число доступных на графе совпадений. Подтверждено кодом |
| Сброс | `resetViewState()` не очищает `timelineCutoff` и `changesHighlight`; `hasActiveViewState()` их не учитывает | Обещание полного сброса требует уточнения. Наличие других путей очистки не исправляет неоднозначность этого действия |
| Теги и папки | `FilterChips.renderMenu()` создаёт весь список; поиска, обработки Escape и восстановления фокуса внутри компонента нет | Длинные списки трудно просматривать; скорость проверить на реальном словаре |
| Клавиатура | `GraphView.handleKeyDown()` слушает document в capture, проверяет видимость, но не принадлежность фокуса панели; исключает INPUT/TEXTAREA/contenteditable, не SELECT | Риск перехвата Space/Backspace в соседней панели, селекте или модальном интерфейсе. Сначала воспроизвести |
| Подписи | `cullAndLabel()` учитывает видимость, глубину, приоритет и бюджет, но не пересечение прямоугольников текста | Возможное наложение подписей в плотных областях. Нужна визуальная проверка |
| Цена ввода | Каждый ввод вызывает `recomputeVisual()`; `currentFocusDistances()` заново строит adjacency и расстояния | Кандидат для объединения обновлений и кеша по версии графа, а не доказанное торможение |
| 3D-подписи | При проходе подписей сортируется массив глубин всех узлов, даже до проверки положительного бюджета | Кандидат для профилирования и небольшого fast path; переписывать выборку заранее не нужно |
| Стиль | `PanelState` не содержит nodeStyle; отдельный план `.plan.md` уже описывает flat/glow/ring | Это существующая запланированная функция; объединить приоритеты, не создавать конкурирующую спецификацию |
| Объяснение цвета | `Legend` объясняет только цвет, числовая шкала показывает min/max без значений | Можно лучше объяснить вид, но польза новой информации требует проверки |

## Критический пересмотр — отдельный проход

Перечитал предложения как новый рецензент, исходя из существующих возможностей и цены ошибок. Это повторная оценка тем же агентом, не независимый аудит или пользовательское тестирование.

| Возражение к первому плану | Решение после пересмотра |
|---|---|
| «Добавить строку состояния» рискует съесть ещё один ряд графа | Расширять существующую строку поиска; показывать сведения только при активных ограничениях. На узкой панели — один раскрываемый элемент «Ограничения: N» |
| «Сбросить всё» может уничтожить полезные настройки | Разделить удаление конкретного ограничения и восстановление временного вида. Пресеты, оформление и закрепления сохранять. Полный сброс настроек оставить отдельной существующей операцией |
| Undo всей сессии — камера, физика, удаления/переименования — слишком сложен | Отложить общую историю. Сначала существующие локальные Undo; при необходимости один снимок временных ограничений перед сбросом |
| Поиск заметок списком дублирует Quick Switcher Obsidian | Отложить до наблюдаемого сценария, где нужен именно список совпадений текущего графа |
| Карточка заметки дублирует hover preview и side pane | Не вводить новую постоянную панель. Сначала коротко объяснить метрики в существующих tooltip/легенде |
| Умное качество может незаметно менять вид и скрывать важное | Сначала замеры. Автоматическую смену подписей/связей не вводить без доказанной необходимости и явной индикации |
| Удаление пересекающихся подписей может скрыть маршрут Explore/Path | Не скрывать обязательные подписи механически. Для них отдельный приоритет; сложные плотные случаи проверять отдельно |
| Задержка одиночного клика 350 мс выглядит как тормоз | Не сокращать наугад: она предотвращает открытие/Hide/Pin перед двойным кликом. Проверить сценарий, добавить мгновенную обратную связь только если она не выполняет действие |
| Переписать рендер «для 50k» — повторение старой ошибки | Профилировать по операциям на 3k/10k/50k. Исторический план уже отменил ParticleContainer, BitmapText и индекс hit-test из-за отсутствия выгоды |
| Большие файлы требуют сначала масштабного рефакторинга | Извлекать только модель временного состояния и чистые функции, необходимые первым изменениям. Остальное не делать блокером |
| Новые визуальные стили приятны, но не помогают понять исчезнувшие узлы | Перенести стили после исправления состояния и проверки подписей; использовать `.plan.md` |

**Итог пересмотра:** первый релиз ограничить объяснением состояния, достоверными счётчиками, восстановлением вида и удобными фильтрами. Читаемость и стиль — следующий этап. Производительность развивается по подтверждённым измерениям, а не общим обещаниям FPS.

## Пересмотренный порядок внедрения

Оценки ниже — относительный объём, не сроки: S — локальное изменение, M — несколько компонентов и интеграционные проверки, L — существенная переработка. Пользовательскую пользу пока оцениваем по сценариям, без вымышленных численных рейтингов.

### Этап 0. Проверить исходное поведение — P0, S–M

- В Obsidian пройти: найти заметку → Focus → вернуться; совместить теги, папку и запрос → получить ноль → восстановить вид; Explore рядом с редактором → использовать клавиатуру.
- Проверить панель 360/600/900/1440 px, светлую/тёмную тему, масштаб интерфейса 100/125/150%, длинные русские названия. Сохранить скриншоты и короткие записи воспроизведения.
- Проверить клавиатуру в двух одновременно видимых графах, соседнем редакторе, SELECT и модальном окне. Если перехват воспроизводится — исправить принадлежность события активному графу до добавления новых действий.
- Зафиксировать baseline поиска и движения камеры на синтетических 3k/10k/50k узлах: p50/p95 времени операции/кадра, длинные задачи, число пересчётов. Описать устройство, число рёбер, режим физики и подписи.

Выход: подтверждённые сценарии проблем и исходные измерения. Наблюдение нескольких человек полезно, но отсутствие дополнительных тестировщиков не блокирует исправление воспроизводимых ошибок.

### Этап 1. Понятное состояние и восстановление — P0, M

Затрагивает `GraphView.ts`, `SearchBar.ts`, `FilterChips.ts`, `TimelineBar.ts`, локали и стили; небольшую модель состояния при необходимости вынести отдельно.

1. Описать временные ограничения отдельно от оформления и долговременных настроек: запрос, теги, папки, скрытые узлы/кластеры, время. Подсветку Changes и режимы Focus/Explore показывать как режимы, не выдавать за фильтры.
2. Считать доступные совпадения с учётом hidden mask. Если нужен общий итог по хранилищу, подписывать его отдельно. Общий счётчик видимости показывать и при фильтрах без текстового запроса.
3. Использовать существующую строку статуса для активных ограничений с адресным снятием. Не складывать числа скрытых узлов по причинам: множества пересекаются.
4. Добавить состояние «Нет заметок при текущих ограничениях» с действиями снятия ограничений. Отличать его от пустого хранилища, загрузки и ошибки; не показывать финальный ноль во время индексации.
5. Уточнить действие восстановления: выйти из Focus/Explore штатными методами, очистить временные ограничения и Changes-подсветку, синхронизировать UI timeline. Сохранить оформление, сохранённые пресеты и явные pins. Не менять камеру без явной причины; отдельная команда кадрирования уже есть.
6. Если добавляется отмена сброса — один снимок временного состояния по путям заметок; камера и физика не входят. Переименованные/удалённые заметки не восстанавливать по старым числовым id.

Приёмка: запрос + теги + папка + время дают объяснимый итог; адресное снятие не трогает соседние условия; восстановление возвращает полный набор доступных узлов без изменения стиля/pins; Controls и команда дают одинаковый результат. Интеграционные тесты комбинаций обязательны.

### Этап 2. Фильтры, которыми удобно пользоваться — P1, M

1. Добавить поле поиска внутри dropdown тегов/папок; выбранные элементы доступны и после сужения списка.
2. Escape закрывает dropdown и возвращает фокус кнопке, Tab проходит нативные checkbox, пробел меняет выбор. Добавить expanded/controls и обозначение текущего состояния.
3. При обновлении словаря согласовать удалённые теги/папки с владельцем фильтра и сохранением настроек: одного обновления checkbox недостаточно.
4. На длинном списке сначала проверить стоимость открытия. Ограниченную выдачу/порционную загрузку вводить при измеримой задержке, с доступом ко всем результатам. Не начинать с виртуализации.
5. Согласовать отступы, размеры кнопок, обрезку длинных названий и видимый фокус в поиске, фильтрах и тулбаре.

Приёмка: нужный тег можно найти вводом части имени среди 1000 значений, выбрать с клавиатуры, закрыть и снять выбор; ноль совпадений объясняется; открытие и ввод не дают длинных задач >50 мс на согласованной тестовой машине. Этот порог — цель, не текущий результат.

**Первый релиз: этапы 0–2.** После проверки на обычном хранилище можно остановиться: это уже самостоятельное улучшение.

### Этап 3. Читаемость графа — P1, M

1. Подтвердить наложение подписей на плотных участках в 2D/3D. Если мешает, добавить проверку пересечений в экранных координатах для обычных подписей.
2. Приоритет: выбранная/наведённая заметка и обязательные названия маршрута, затем остальные. Обеспечить стабильность выбора при небольшом движении камеры; не допустить мерцания от пересортировки.
3. Сохранить бюджет создания текста; не измерять размеры всех названий каждый кадр. Пространственное ускорение вводить по результату профиля.
4. Проверить hover preview: дефолт 300 слов может перекрывать большую часть небольшой панели. Сначала протестировать ограничение высоты/короткий preview; полный текст уже доступен в заметке.

Приёмка: обычные подписи не перекрываются в фиксированных проверочных сценах; выбранная заметка остаётся узнаваемой; маршрут не теряет названия; p95 кадра не ухудшается более чем на 10% относительно одинакового baseline. Допустимый порог уточнить после этапа 0.

### Этап 4. Внешний вид и объяснение метрик — P2, M

- Реализовать существующий `.plan.md` про flat/glow/ring после проверки совместимости со светлой темой, локальным графом и legacy-пресетами. Не менять существующий вид при миграции.
- В существующей легенде/tooltip объяснить, какая метрика отвечает за размер и цвет. Числовые границы показывать только если они точно соответствуют нормализации, используемой в encoding.
- Сначала улучшить существующие пресеты; новые добавлять только для отдельной полезной задачи. Не увеличивать Simple-панель ещё одной группой экспертных настроек.

Приёмка: пользователь может объяснить размер/цвет выбранного узла; смена стиля не меняет семантику метрик; старые сохранённые виды после обновления выглядят как прежде.

### Отдельная ветка: измеримая производительность — P1 по результатам этапа 0

Порядок кандидатов: объединение частых `recomputeVisual()` в один запланированный проход с актуальным состоянием → кеш adjacency/Focus distances по версии графа, корню и глубине → исключение лишних аллокаций выбранных тегов/папок в цикле → быстрый выход перед сортировкой глубин при отсутствии обычных подписей → более сложный выбор подписей только по профилю.

При планировании обновлений Enter/очистка не должны проигрывать устаревшему отложенному вводу. При кешировании удаления, переименования и смена topology обязаны инвалидировать данные. Проверить lifecycle content-index jobs отдельно: отмена/устаревание результатов при закрытии и перестроении графа.

Остановку ticker/worker в скрытой панели рассматривать отдельно после замера фоновой нагрузки; восстановление должно сохранять pins, камеру, Explore и незавершённые расчёты. Не связывать это с автоматической сменой визуального качества.

Приёмка каждой оптимизации: одинаковые входные данные, до/после, несколько прогонов, корректность результатов и отсутствие регрессий drag/поиска/навигации. Если выигрыш в пределах шума — изменение исключить. Замена движка, ParticleContainer, BitmapText, ping-pong buffers в этот план не входят.

## Порядок PR и выпуск

1. Документированные воспроизведения и baseline; при подтверждении — отдельный fix клавиатурного scope.
2. Достоверные счётчики и модель состояния, без визуальной переделки.
3. Активные ограничения, состояние нулевого результата, восстановление вида.
4. Поиск и клавиатурное управление фильтрами, затем проверка в Obsidian и небольшой релиз.
5. Читаемость подписей отдельным PR после сравнения сцен.
6. Стиль узлов по существующему плану; пояснения метрик отдельно.
7. Оптимизации — отдельные PR на каждый подтверждённый источник задержки, без ожидания визуального этапа.

Для каждого изменения: относящиеся к сценарию тесты, `npm run verify`, `npm run build`, ручная проверка затронутого поведения в Obsidian, все 12 локалей для новых строк. Миграции проверять на старых настройках и пресетах. CSS/размещение и скорость GPU нельзя принять по jsdom-тестам.

Откат: независимые изменения небольшими PR, сохранение обратной совместимости настроек, отсутствие удаляющих миграций. Старые завершённые планы не переписывать; текущий документ дополняет UI-спецификацию и ссылается на существующий план стилей.

## Что пока не делать

AI-помощник, автоматические рекомендации связей, новый dashboard, миникарта, облачные функции, общий Undo/Redo, полная история камеры, массовый рефакторинг, новый renderer. У этих идей сейчас нет подтверждённой пользы, оправдывающей отвлечение от навигации, читаемости и ясности состояния.
